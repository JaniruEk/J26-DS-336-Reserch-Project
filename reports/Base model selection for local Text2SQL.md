# Switch the shared base to Qwen2.5-Coder-1.5B

The team should drop Phi-3 Mini 3.8B as the shared placeholder and standardise now on **Qwen2.5-Coder-1.5B-Instruct**. It serves as the placeholder for Agents 3 and 4, as the native baseline, and as the starting point for the distilled student. **Qwen2.5-Coder-7B-Instruct** is the same-tokenizer teacher. All three checkpoints are Apache 2.0. The pairing has the strongest published Text-to-SQL evidence at ≤1.5B: in the only like-for-like small-model study, the 1.5B model reached **67.08% BIRD dev EX** after fine-tuning, using exactly this 7B teacher ([SLM-SQL](https://arxiv.org/abs/2507.22478)). A 1.5B model also trains in plain 16-bit LoRA on the 8GB RTX 3070 Ti, where Phi-3 Mini can only be trained as QLoRA. Phi-3 Mini also has no ~7B sibling that shares its tokenizer. Keeping it would turn Agent 3's and Agent 4's placeholder experiments into throwaway work and confound the QAT-vs-PTQ study. Hand off checkpoints as Hugging Face safetensors folders and PEFT adapter folders in private Hub repos. Hand off quantized models as GGUF (deployment) and llm-compressor AWQ (comparison). Train on Kaggle "T4 x2", not P100, and serve on the local Ampere card. Methodologically, the biggest risk is statistical, not the choice of model. At n≈128 only differences of about 10 points or more are detectable. Each agent needs ≥600 paired evaluation items, greedy decoding, ≥3 seeds for trained arms, oracle and control arms, and one pre-registered primary comparison. The fallback is the Qwen3 family (Qwen3-8B teacher → Qwen3-1.7B/0.6B student).

## Phi-3 Mini fails three of the project's own constraints

Phi-3 Mini is 3.8B parameters under MIT. That is outside the proposal's 0.5–1.5B student range. Its only ~7B sibling, Phi-3-small, uses a **different ~100,352-token vocabulary** ([Phi-3-small card](https://huggingface.co/microsoft/Phi-3-small-8k-instruct)). Agent 2 therefore has no clean same-family teacher. Hardware is the second problem. Unsloth's official minimums are **3.5 GB for QLoRA and 8 GB for 16-bit LoRA on a 3B model**, and Unsloth calls these "the absolute minimum" ([Unsloth requirements](https://www.unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements)). At bf16, Phi-3 Mini's weights alone take about 7.6 GB, so on the target GPU it can only be trained as 4-bit QLoRA. That has two knock-on effects. Agent 3's LoRA-vs-HydraLoRA comparison becomes a QLoRA comparison. Agent 4's QAT-vs-PTQ comparison then starts from a base that was already NF4-quantized during training, which mixes quantization effects into the fine-tuning results.

The third problem is transfer. Quantization sensitivity and adapter capacity both scale with model size, so a Phi-3 3.8B result tells the team little about a 1.5B student. The tokenizer also changes from Phi-3's 32K vocabulary to Qwen's ~151K. That changes token counts, which are Agent 1's headline efficiency metric, along with prompt templates and chat formats. Phi-3 still has a place, as an external reference point. Agent 1's existing phi3 stand-in figures (about 0.40 execution accuracy on 128 Chinook+Spider queries) should be reported as the "off-the-shelf 3.8B general model" baseline. It should not be the trained base.

## Qwen2.5-Coder 7B→1.5B is the best-evidenced, lowest-risk pairing

The candidate field is narrow. Only the Qwen and Llama families offer a permissively licensed sub-2B model *and* a same-tokenizer 7–9B teacher. SmolLM2 and Gemma 3 1B have no 7B sibling. DeepSeek-Coder-1.3B dates from 2023 and has a 16K context. Llama-3.2-1B has a weaker SQL baseline, and its licence requires any distributed derivative to be **prefixed "Llama" and to display "Built with Llama"** ([Llama 3.2 licence](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct/blob/main/LICENSE.txt)). That is awkward for a licensed on-premise appliance. Qwen2.5-Coder-1.5B-Instruct has 1.54B parameters, 28 layers and a 32,768-token context, under Apache 2.0 ([HF card](https://huggingface.co/Qwen/Qwen2.5-Coder-1.5B-Instruct)). One trap: the **3B Coder size is under the non-Apache "qwen-research" licence** ([HF card](https://huggingface.co/Qwen/Qwen2.5-Coder-3B-Instruct)), so do not drift to 3B.

The SQL evidence favours this family. SLM-SQL fine-tuned five small models on the same data with Qwen2.5-Coder-7B-Instruct as teacher, then added RL and self-consistency. The 1.5B model ended highest at **67.08% BIRD dev**, against **56.87% for the 0.5B** ([SLM-SQL](https://arxiv.org/abs/2507.22478)). The paper reports an average gain of 31.4 points across the five models. The teacher side is also well supported. Qwen2.5-Coder-7B-Instruct scores 73.4 Spider dev / 50.9 BIRD dev untuned, and it is the base of OmniSQL-7B, which reaches 81.2 / 63.9 ([OmniSQL](https://arxiv.org/html/2503.02240v2)). Generating 3,000 teacher responses is cheap. A 7B model under vLLM produces about **3–4k tokens/s on a single 24GB card** ([DatabaseMart benchmark](https://databasemart.com/blog/vllm-gpu-benchmark-rtx4090)). By our estimate, the whole teacher pass takes 20–30 minutes, or a few hours with 8 samples per prompt for execution filtering.

Two cautions keep the claim honest. First, response-based (sequence-level) distillation only exchanges text, so it does not strictly need a shared tokenizer. DeepSeek-R1-Distill-Qwen-1.5B was trained across families on 800k teacher samples ([HF card](https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B)). A same-family teacher is still preferable because it keeps chat templates and SQL style consistent and keeps logit-level KD (TRL GKD) open as an ablation ([TRL GKD](https://huggingface.co/docs/trl/main/en/gkd_trainer)). Second, the big published gains come from 10^5–10^6 examples, often with RL on top. The only small-data SQL distillation result we found used **1,000 examples on a 4B student**. It went 17.0 → 34.3 with gold-SQL SFT and → 45.0 with structured chain-of-thought distillation ([Struct-SQL](https://arxiv.org/html/2512.17053v3)). Most of that jump came from fine-tuning itself, not from the teacher. Agent 2 should therefore expect smaller, noisier effects at 1.5–3k pairs than the headline literature numbers suggest.

**Fallback: Qwen3-8B → Qwen3-1.7B / 0.6B.** These are Apache 2.0 with a 151,669-token vocabulary, and Qwen3-0.6B has a strong untuned baseline. However, the Qwen3 small models were **already built by strong-to-weak distillation from Qwen3-32B/235B** ([Qwen3 report](https://arxiv.org/html/2505.09388)). Any "native vs distilled" claim would then become "extra task-targeted distillation on an already-distilled model". The newest small Qwen, Qwen3.5-0.8B/2B, is not recommended for now. It uses a hybrid Gated-DeltaNet architecture with a vision encoder and a new **248,320-token vocabulary**, and needs transformers from main or vLLM nightly ([HF card](https://huggingface.co/Qwen/Qwen3.5-0.8B)). Its teacher would be 9B, and it has no published SQL result. Our inference is that AWQ, GGUF and PEFT tooling for this architecture is not yet mature enough to build on. A 0.5B variant of the primary pairing is a valid second student size if the team wants more headroom over a weaker baseline and a cheaper quantization study.

## Hand-off formats and platforms the team can freeze this week

Use the formats the tooling already treats as standard. **Agent 2 → Agent 3:** full bf16 Hugging Face folders (`config.json`, `generation_config.json`, `*.safetensors`, tokenizer and chat template) in a private HF Hub repo, tagged `native-v1` and `distilled-v1`, with the base commit hash recorded. **Agent 3 → Agent 4:** standard LoRA ships as a PEFT adapter folder (`adapter_config.json` + `adapter_model.safetensors`), the unit PEFT loads and composes ([PEFT LoRA guide](https://huggingface.co/docs/peft/developer_guides/lora)). HydraLoRA ships as `hydra_adapter.safetensors` plus a `hydra_config.json` (rank, alpha, target modules, head→complexity-bucket map). Agent 3 should also provide merged-per-head HF folders so Agent 4 can quantize with standard converters. llama.cpp's `convert_lora_to_gguf.py` accepts the PEFT format directly ([llama.cpp](https://github.com/ggml-org/llama.cpp)).

**Agent 4 outputs:** GGUF files for deployment and an AWQ folder for comparison, with the quantization recipe saved alongside each. Ollama/llama.cpp runs natively on Windows on CPU or GPU and is already what the harness uses. Build AWQ with **vLLM's llm-compressor, not AutoAWQ**. AutoAWQ was archived in May 2025, with Torch 2.6 / Transformers 4.51.3 as its last tested stack ([AutoAWQ](https://github.com/casper-hansen/AutoAWQ); [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/auto_awq/)). llm-compressor outputs compressed-tensors for vLLM ([llm-compressor](https://github.com/vllm-project/llm-compressor)), which needs WSL2/Docker on Windows.

HydraLoRA needs its own module. The official repo is a modified PEFT fork with a *learned* router and K-means head count, last updated December 2024 and with no clearly stated licence ([GitHub](https://github.com/Clin0212/HydraLoRA)). PEFT has no shared-A / multi-B variant, and its X-LoRA uses a learned classifier with two forward passes per step ([PEFT X-LoRA](https://huggingface.co/docs/peft/package_reference/xlora)). A roughly 50-line custom wrapper (shared A, four B heads, head index set from Agent 1's complexity label, batches grouped by bucket) is less work and avoids version lock. It should be described as "HydraLoRA-style asymmetric LoRA with rule routing", citing the paper for the architecture only ([arXiv 2404.19245](https://arxiv.org/html/2404.19245v2)). A 2026 study finding that hard routing matches or beats soft routing for LoRA mixtures supports the hard-coded design ([arXiv 2606.31413](https://arxiv.org/pdf/2606.31413)).

QAT also needs honest framing. Practical LLM QAT in 2026 means torchao, either directly or via Unsloth's `qat_scheme`, which works with LoRA. It exports torchao formats, not GGUF or AWQ ([Unsloth QAT](https://unsloth.ai/docs/blog/quantization-aware-training-qat)). torchao reported that QAT recovered **96% of hellaswag and 68% of wikitext-perplexity degradation** versus PTQ on Llama3-8B ([PyTorch blog](https://pytorch.org/blog/quantization-aware-training/)). The defensible design has two arms. One trains with an int4 weight-only fake-quantizer whose group size matches the target (32 for GGUF Q4_0, 128 for AWQ) and then exports through the normal converters. The other applies PTQ (RTN, imatrix, AWQ) to the non-QAT model through the same converters. Google's Gemma 3 QAT checkpoints shipped as GGUF Q4_0 follow this same pattern ([lmstudio-community](https://huggingface.co/lmstudio-community/gemma-3-4B-it-qat-GGUF)). AWQ is itself a PTQ algorithm, so "QAT in AWQ format" is not a valid claim. At 8-bit, Q8_0 PTQ is typically near-lossless, so a null QAT result is likely and still legitimate.

**Platform.** Separate the training budget (≤16 GB cloud) from the serving budget (8 GB local). Kaggle offers about 30 GPU-hours a week with 12-hour sessions, on either a P100 or two T4s ([gpuperhour](https://gpuperhour.com/blog/free-cloud-gpus-and-credits)). **Choose T4 x2, never P100.** The P100 is compute capability 6.0, below Unsloth's 7.0 minimum ([Unsloth](https://www.unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements)) and AWQ's 7.5 ([AutoAWQ](https://github.com/casper-hansen/AutoAWQ)), and it lacks bf16. The T4 also lacks bf16, so cloud runs use fp16. Colab free gives at most 12 hours on unguaranteed GPU types ([Colab FAQ](https://research.google.com/colaboratory/faq.html)). For reproducibility, pin one platform for all reported runs. The local RTX 3070 Ti (Ampere, compute 8.6, bf16, Marlin AWQ kernels) is the team's best inference target and can run 1.5B 16-bit LoRA itself. Measuring peak VRAM at 1k/2k tokens with `torch.cuda.max_memory_allocated()` takes about an hour and gives reportable evidence, because no primary source measured it for these sizes.

## Statistical power, not model choice, decides whether results are trustworthy

The current evidence already shows the problem. In the pruning-vs-hybrid comparison, 26 of 128 items were discordant (p_d ≈ 0.20). Using a normal approximation for McNemar's test (our calculation, α=0.05, power 0.80), detecting a **5-point EX difference needs about 626 paired items**, a 3-point difference about 1,742, and only a 10-point difference fits in about 155. This matches the broader finding that NLP comparisons are routinely underpowered ([Card et al. 2020](https://arxiv.org/pdf/2010.06595)). Each agent's headline comparison should pool Spider dev (1,034 items), the Chinook pairs and TPC-H into a set of at least 600–1,000. Per-bucket results should be reported descriptively, with bootstrap CIs and discordant counts. Trained arms need at least 3 seeds, because seed variance can exceed the effect size. The team should pre-register one primary comparison per agent and apply Holm-Bonferroni to secondary comparisons and buckets ([Dror et al. 2018](https://aclanthology.org/P18-1128/)).

The pruning result should be read as expected, not as a failure. The literature finds that schema filtering helps fine-tuned small and mid-size models only modestly, and only at near-perfect recall. CodeS lost 0.8–2.4 Spider dev points without its filter, and it padded training prompts with random unused tables to avoid train/test mismatch ([CodeS](https://arxiv.org/html/2402.16347v1)). DTS-SQL's 7B generators gained 3–7 points from a linker with about 98% table recall, with gold schema adding another 5–8 ([DTS-SQL](https://arxiv.org/html/2402.01117)). When filtering cut recall to 77%, strong models lost 3–5 points while weaker ones gained ([Maamari et al.](https://arxiv.org/html/2408.07702v2)). The phi3 runs were *untrained* on pruned context, so they cannot test the hypothesis that matters. That hypothesis is a 2×2 design: training context {table-level, pruned} × test context {table-level, pruned}, run on the fine-tuned 1.5B. It should be paired with an oracle-columns arm parsed from gold SQL to bound the possible gain.

Five further controls guard against common pitfalls. Agent 2 needs a **"same prompts, gold-SQL targets" SFT control** (C0) alongside the native, native+LoRA, distilled and distilled+LoRA arms. Without it, any distillation gain could simply be more in-domain SFT, as Struct-SQL's ablation shows ([Struct-SQL](https://arxiv.org/html/2512.17053v3)). Teacher prompts must come only from Spider/BIRD *train* and synthetic DBs, never from the Spider dev DBs that Agent 1's `eval/spider_pairs.json` draws on. Spider is contaminated in pretrained LLMs: GPT-3.5 scored 10–20 points lower on an unseen equivalent ([Ranaldi et al.](https://arxiv.org/html/2402.08100v1)). Report the team-written Chinook pairs as the deployment-relevant number and Spider as the literature-comparable number. All arms should use greedy decoding, because published small-model figures often use self-consistency and are not comparable to single-shot results. Run the official test-suite evaluator on Spider items to cross-check the in-house row-multiset scorer ([test-suite-sql-eval](https://github.com/taoyds/test-suite-sql-eval)). Treat BIRD Mini-Dev as secondary only: a 2026 audit found **52.8% annotation errors**, enough to reorder rankings ([Jin et al.](https://arxiv.org/abs/2601.08778)).

## Conclusion

Choosing the model is the easy part. Qwen2.5-Coder 7B→1.5B removes three confounds at once: tokenizer mismatch, QLoRA-only training, and non-transferable placeholder results. It also lets every agent work on the final architecture from now on, so "placeholder" runs become pilot runs of the real system rather than rehearsals. The harder change is to evaluation scale and design. The project's honest contribution is careful measurement on an 8GB budget, and at n≈128 that measurement cannot separate a real 5-point effect from noise. Neutral or negative findings, such as pruning failing to help or 8-bit QAT matching PTQ, only become publishable evidence when the test was powered to detect an effect.

The one result most likely to make the dissertation stand out has not been run yet: whether a 1.5B model *fine-tuned on pruned context* recovers the multi-join accuracy that an untrained phi3 lost. The literature predicts small gains conditional on near-perfect recall. The team's own data shows recall is the binding constraint. A powered 2×2 test on the shared Qwen base turns those two observations into a falsifiable claim.
