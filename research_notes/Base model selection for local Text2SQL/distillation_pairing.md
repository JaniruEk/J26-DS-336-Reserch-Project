# Teacher / Student / Native-Baseline Selection for Response-Based KD (Text-to-SQL), Oct 2026

Scope: Agent 2 (Wathsala). ~7B teacher run on rented GPU for inference only; student 0.5–1.5B trained by SFT on 1,500–3,000 teacher responses; compared against a native model of identical size/tokenizer, before and after identical LoRA fine-tuning; 8GB VRAM for training.

## Q1. Which families give a strong ~7B teacher plus same-tokenizer small siblings? Does response-based KD need a shared tokenizer?

### Takeaway
Qwen2.5-Coder (7B → 0.5B/1.5B) is the best-evidenced Text-to-SQL family and is Apache 2.0 at those sizes; Qwen3 (8B → 0.6B/1.7B) is a strong Apache 2.0 alternative. Response-based (sequence-level) KD only exchanges text, so it does NOT need a shared tokenizer; logit-based KD (GKD/JSD, MiniLLM-style) does, unless you use cross-tokenizer methods (ULD/GOLD).

### Cited Findings
- OmniSQL-7B is built on Qwen2.5-Coder-7B-Instruct and raises its average across benchmarks from 52.8% to 61.2% (+8.4); 87.9% on Spider test (greedy), 88.9% with majority voting. OmniSQL exists only at 7B/14B/32B (no 0.5B/1.5B) — [OmniSQL, arXiv 2503.02240](https://arxiv.org/html/2503.02240v2)
- SynSQL-2.5M (2.5M samples, >16k synthetic DBs) was generated by Llama3.1, DeepSeek-Coder, Qwen2.5 and Qwen2.5-Coder; OmniSQL training also included Spider and BIRD train sets — [OmniSQL](https://arxiv.org/html/2503.02240v2)
- Qwen2.5-Coder's Text-to-SQL ability was enhanced with synthetic SQL data in pre-training and fine-tuning; evaluated on Spider and BIRD with a unified prompt — [Qwen2.5-Coder Technical Report, arXiv 2409.12186](https://arxiv.org/pdf/2409.12186)
- Qwen2.5-Coder-1.5B-Instruct: Apache 2.0, 1.54B params (1.31B non-embedding), 28 layers, 32,768 context — [HF model card](https://huggingface.co/Qwen/Qwen2.5-Coder-1.5B-Instruct)
- Qwen2.5-Coder-3B-Instruct is under the "qwen-research" licence (not Apache) — [HF model card](https://huggingface.co/Qwen/Qwen2.5-Coder-3B-Instruct)
- On BIRD, Qwen2.5-Coder dominates older CodeLlama at matched size (39.1 vs 20.9 at 7B) in an on-prem study; that study evaluated no models ≤2B — [arXiv 2606.29733](https://arxiv.org/abs/2606.29733)
- SLM-SQL (2025) compared five small students and used Qwen2.5-Coder-7B-Instruct as the teacher generating 8 CoT candidates per question (voted) to build SynSQL-Think-916K — [SLM-SQL, arXiv 2507.22478](https://arxiv.org/html/2507.22478)
- Qwen3 tokenizer: byte-level BPE, vocabulary 151,669; all Qwen3 models Apache 2.0 — [Qwen3 Technical Report, arXiv 2505.09388](https://arxiv.org/html/2505.09388)
- TRL GKDTrainer computes token-level generalized JSD between student and teacher distributions (`seq_kd=True` = SFT on teacher output); its examples pair same-family models (Qwen2-0.5B student, Qwen2-1.5B teacher) — [TRL GKD docs](https://huggingface.co/docs/trl/main/en/gkd_trainer)
- TRL GOLD (experimental) extends Universal Logit Distillation to support "student/teacher pairs with different tokenizers" by aligning text spans and merging probabilities; same-tokenizer pairs use plain JSD — [TRL GOLD docs](https://huggingface.co/docs/trl/main/en/gold_trainer)
- DeepSeek-R1-Distill-Qwen-1.5B is response-based KD across families (DeepSeek-R1 teacher → Qwen2.5-Math-1.5B student, 800k samples), proving shared tokenizer not needed for sequence-level KD — [HF model card](https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B)

### Inferences
- Recommended triples (teacher → distilled student vs native baseline):
  1. **Primary:** Qwen2.5-Coder-7B-Instruct → Qwen2.5-Coder-1.5B-Instruct (distilled) vs Qwen2.5-Coder-1.5B-Instruct (native). Strongest SQL evidence (SLM-SQL used exactly this teacher), Apache 2.0 on all three, same tokenizer family so a logit-KD extension remains possible. 1.5B fits LoRA/QLoRA on 8GB.
  2. **Low-budget variant:** same teacher → Qwen2.5-Coder-0.5B-Instruct. Larger headroom (weaker baseline) so effects easier to detect; also the cheapest for Agent 4 quantization.
  3. **Alternative:** Qwen3-8B (non-thinking or thinking mode as teacher) → Qwen3-1.7B / Qwen3-0.6B. Apache 2.0, newer, but see Q2 confound.
  4. **Not recommended as primary:** Llama-3.1-8B → Llama-3.2-1B (weak SQL baseline, naming/attribution licence duties); OmniSQL-7B as teacher (strongest SQL teacher, but trained on Spider/BIRD train — fine for response generation if eval sets are Chinook/held-out, otherwise leakage risk; check its licence before use — not verified here); Qwen2.5-Coder-3B (research licence; also exceeds 0.5–1.5B range).
- Avoid the Qwen2.5-Coder-3B middle size if the project wants commercial-appliance framing.
- For a pure SFT-on-teacher-text design, a cross-family teacher would also work; same-family is still preferred because it keeps chat templates and SQL style consistent and leaves logit KD as an optional ablation.

### Gaps
- Did not verify whether Qwen2.5-Coder-0.5B/1.5B and 7B have identical embedding-matrix sizes (padded vocab can differ between sizes even with the same tokenizer); must check `config.json` `vocab_size` before attempting logit KD.
- OmniSQL-7B licence and DeepSeek-Coder licence terms on output use were not checked.
- Phi (Microsoft) licence not checked this session.

## Q2. What is a fair "native baseline", and how do you isolate distillation as the only variable?

### Takeaway
The native baseline is the off-the-shelf instruct checkpoint of the exact same model the student starts from — the student is that checkpoint + teacher-response SFT. Isolating distillation additionally requires a "same prompts, non-teacher targets" control, because SFT itself (not the teacher) can explain gains. Note that modern small "native" models are already distilled by their vendors.

### Cited Findings
- Struct-SQL's ablation shows why a control is needed: Qwen3-4B student on BIRD mini-dev — base 17.0% EX; SFT on gold SQL only 34.3%; unstructured CoT distillation (GPT-4o teacher) 36.9%; structured (query-plan) CoT distillation 45.0%. Most of the jump from base came from fine-tuning itself; the teacher-specific gain over gold-SQL SFT was +2.6 (unstructured) / +10.7 (structured) — [Struct-SQL, arXiv 2512.17053](https://arxiv.org/html/2512.17053v3)
- Qwen3-0.6B/1.7B/4B/8B/14B were themselves built with "strong-to-weak distillation" (off-policy teacher outputs + on-policy logit KD from Qwen3-32B or Qwen3-235B-A22B) — [Qwen3 Technical Report](https://arxiv.org/html/2505.09388)
- Llama 3.2 1B/3B incorporated logits from Llama 3.1 8B and 70B during pre-training after pruning — [PyTorch/torchtune KD tutorial context](https://docs.pytorch.org/torchtune/0.4/tutorials/llama_kd_tutorial.html); [search summary, secondary](https://pytorch.org/?p=2785)

### Inferences
- Minimal valid design (4 arms × same eval set):
  - A: native student (off-the-shelf instruct).
  - B: native + LoRA (Agent 3's recipe).
  - C: distilled student (native + SFT on teacher responses).
  - D: distilled + identical LoRA.
  - Recommended extra control C0: native + SFT on the *same prompts* with gold/reference answers (or answers from the student itself / a same-size model). C vs C0 isolates the teacher's contribution from "more SFT steps on in-domain prompts".
- Hold fixed across arms: prompt template/chat template, max sequence length, decoding (greedy, temperature 0), LoRA rank/alpha/target modules/lr/epochs/seed, number of training tokens, eval set and execution-accuracy scorer. Run ≥3 seeds or bootstrap CIs + McNemar (already in repo's `stats.py`).
- Frame the claim as "additional task-targeted distillation on top of an already-distilled native model", since Qwen3 and Llama 3.2 small models are vendor-distilled. Qwen2.5-Coder small models' report does not (as far as checked) describe strong-to-weak distillation, making them a cleaner "native" baseline — unverified, see gap.
- Filter teacher responses by execution correctness (where gold exists) — otherwise the distilled arm inherits teacher errors; report filtering rate.

### Gaps
- Not verified whether Qwen2.5-Coder-0.5B/1.5B were trained with distillation from larger Qwen models.

## Q3. Published evidence on distilling SQL/code ability into ≤1.5B (and nearby) models — data sizes and gains

### Takeaway
Large gains are reported, but almost always with 10^5–10^6 examples and often RL on top; the only small-data SQL result found (1,000 examples) used a 4B student. Expect smaller, noisier effects at 1.5–3k pairs.

### Cited Findings
- SLM-SQL (2025): Qwen2.5-Coder-7B-Instruct teacher, SynSQL-Think-916K (916,156 CoT examples) + SynSQL-Merge-Think-310K; SFT then RL (GRPO-style) + corrective self-consistency. Reported (base → SFT → SFT+RL): Qwen2.5-Coder-0.5B-Instruct 42.13 → 65.31 → 70.60; Qwen3-0.6B 63.19 → 68.02 → 72.05; Llama-3.2-1B-Instruct 30.79 → 63.77 → 67.63; DeepSeek-Coder-1.3B-Instruct 48.23 → 72.86 → 75.47; Qwen2.5-Coder-1.5B-Instruct 63.54 → 74.53 → 75.15. Abstract: avg +31.4 pts on BIRD; 0.5B 56.87% and 1.5B 67.08% BIRD dev EX — [SLM-SQL, arXiv 2507.22478](https://arxiv.org/html/2507.22478) (abstract: [arXiv abs](https://arxiv.org/abs/2507.22478))
  - Caution: the per-model table values (e.g., 75.15) exceed the abstract's BIRD dev numbers (67.08), so the table is likely on a different benchmark (probably Spider) or setting; the fetch tool did not disambiguate. Verify in the PDF before citing.
- Struct-SQL: GPT-4o teacher → Qwen3-4B, only **1,000 BIRD training examples** stratified by SQL complexity; structured CoT distillation 45.0% vs unstructured 36.9% vs gold-SQL SFT 34.3% vs base 17.0% (BIRD mini-dev EX); gain attributed to fewer syntactic/schema-hallucination errors — [arXiv 2512.17053](https://arxiv.org/html/2512.17053v3)
- SQuaD-SQL (2026): LLM-generated synthetic data + PEFT on a single consumer GPU; 86.9% EX on WikiSQL test (single-table, easy benchmark) — [arXiv 2607.08161](https://arxiv.org/abs/2607.08161)
- OmniSQL-7B: +8.4 avg over Qwen2.5-Coder-7B-Instruct with ~2.5M training samples — [arXiv 2503.02240](https://arxiv.org/html/2503.02240v2)
- DeepSeek-R1-Distill-Qwen-1.5B: 800k R1 samples; AIME24 28.9, MATH-500 83.9, LiveCodeBench 16.9 — [HF card](https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B)
- Distilling step-by-step: rationale + label multi-task training lets a 770M T5 outperform 540B PaLM using 80% of a benchmark's data; outperforms standard fine-tuning/distillation with fewer labelled examples — [arXiv 2305.02301](https://arxiv.org/abs/2305.02301)
- GKD (on-policy distillation) authors find on-policy data (high `lmbda`) performs better; optimal divergence (`beta`) is task-dependent — [TRL GKD docs](https://huggingface.co/docs/trl/main/en/gkd_trainer)
- Qwen3 report: strong-to-weak distillation outperformed RL for small models at ~1/10 of the GPU cost — [arXiv 2505.09388](https://arxiv.org/html/2505.09388)

### Inferences
- Rationale/CoT-style teacher responses (and structured ones, per Struct-SQL) are the most data-efficient form of response-based KD; recommend the teacher emit a short structured reasoning (tables → joins → filters → aggregation) followed by final SQL, with the student trained on both.
- MiniLLM (reverse-KL) / DistiLLM require logits → need same vocab and teacher loaded during training; with a 7B teacher this does not fit 8GB alongside training, so they are out of scope unless teacher logits are precomputed (top-k) on the rented GPU. Treat as future work.

### Gaps
- Did not fetch MiniLLM/DistiLLM papers directly; no verified numbers for them here.
- Found no published SQL KD study with a ≤1.5B student and ≤3k examples — this is both a risk and a possible contribution angle.

## Q4. Is 1,500–3,000 pairs enough? Data mix, leakage, and licences

### Takeaway
1–3k is in the range where at least one SQL KD paper (1,000 examples, 4B student) showed large, significant differences, so a measurable effect is plausible — but the key comparison should be against an equal-size SFT control, and eval sets must be disjoint from teacher prompts. Qwen (0.5B/1.5B/7B, Qwen3) is Apache 2.0 — no output-use restriction; Llama requires "Llama"-prefixed names + "Built with Llama"; Gemma makes distilled models "Model Derivatives" bound by Gemma terms.

### Cited Findings
- Struct-SQL used 1,000 examples stratified by SQL complexity and obtained 17.0 → 45.0 EX — [arXiv 2512.17053](https://arxiv.org/html/2512.17053v3)
- OmniSQL trains on Spider and BIRD training sets together with synthetic data — [arXiv 2503.02240](https://arxiv.org/html/2503.02240v2) (implies OmniSQL-based teachers have seen those train sets; dev/test still separate)
- Llama 3.1 licence: "If you use the Llama Materials or any outputs or results of the Llama Materials to create, train, fine tune, or otherwise improve an AI model, which is distributed or made available, you shall also include 'Llama' at the beginning of any such AI model name"; must display "Built with Llama"; >700M MAU needs separate licence — [Llama 3.1 LICENSE](https://raw.githubusercontent.com/meta-llama/llama-models/main/models/llama3_1/LICENSE)
- Llama 3.1 was the first Llama licence to allow outputs to improve other models — [Simon Willison on Llama 3.1](https://simonwillison.net/2024/Jul/23/introducing-llama-31)
- Gemma Terms: "Model Derivatives" include models created by transfer of patterns of weights/Output, including distillation and "methods based on the generation of synthetic data Outputs by Gemma for training that model"; Outputs themselves are not derivatives; distributed derivatives must carry the Gemma use restrictions, Notice file and copy of the agreement — [Gemma Terms of Use](https://ai.google.dev/gemma/terms)
- Qwen3: all models Apache 2.0 — [arXiv 2505.09388](https://arxiv.org/html/2505.09388); Qwen2.5-Coder-1.5B-Instruct Apache 2.0 — [HF](https://huggingface.co/Qwen/Qwen2.5-Coder-1.5B-Instruct); Qwen2.5-Coder-3B qwen-research — [HF](https://huggingface.co/Qwen/Qwen2.5-Coder-3B-Instruct)
- Secondary source: some larger Qwen2.5 models (e.g., 72B) carry a "Qwen" licence requiring "Built with Qwen"/"Improved using Qwen" attribution for derivatives — [softwareseni comparison (secondary)](https://www.softwareseni.com/llama-mistral-deepseek-and-qwen-licence-terms-compared-for-commercial-use/)

### Inferences
- Suggested mix for ~2,500 pairs (aligned with the project's taxonomy): ~60–70% SQL-adjacent (NL→SQL with reasoning, schema comprehension Q&A: "which tables/columns answer X", FK path explanation), stratified equally across simple / single-join / multi-join / aggregation; ~30–40% general reasoning to limit catastrophic forgetting. Hold out 10% for validation loss.
- Prompt sources: Spider **train** and BIRD **train** questions/DBs, plus synthetic DBs/questions (Python-generated like the repo's synthetic pairs). Never draw teacher prompts from Spider dev/test, BIRD dev, or the Chinook/TPC-H eval files used by Agent 1/3/4; dedupe by DB name and n-gram overlap of questions. Note that Agent 1's `eval/spider_pairs.json` is drawn from Spider dev — that DB set must be excluded from teacher prompts.
- Power: with ~130–500 eval questions, McNemar can detect differences of roughly ≥5–8 points; plan the eval set size accordingly (inference, not from a source).
- Licence choice: Qwen family avoids naming/attribution duties for a "licensed on-premise appliance" framing; if Llama is used, the distilled student must be named "Llama-…".

### Gaps
- No source found giving a minimum-sample-size rule for detecting KD effects in SQL; effect-size planning is an inference.
- No published decontamination procedure for Spider/BIRD was found in OmniSQL (fetch tool reported none).

## Q5. Teacher inference cost/time for ~3,000 prompts

### Takeaway
Trivial: a 7B model under vLLM produces ~3–4k output+input tokens/s on a single 24–80GB GPU, so 3,000 prompts (even with 8 samples each for voting/filtering) take minutes to ~1–2 hours.

### Cited Findings
- vLLM offline, RTX 4090 (24GB), 100 in / 600 out tokens, 300 requests: DeepSeek-R1-Distill-Qwen-7B 4,172.8 tok/s (5.96 req/s); Llama-8B distill 2,769.3 tok/s — [DatabaseMart RTX4090 vLLM benchmark](https://databasemart.com/blog/vllm-gpu-benchmark-rtx4090)
- ~3,363 tok/s for a 7B model (DeepSeek-R1-Distill-Qwen-7B) on single A100 80GB with default vLLM config — [morphllm vLLM benchmarks (secondary)](https://www.morphllm.com/vllm-benchmarks)
- SLM-SQL generated 8 candidates per question from the 7B teacher and voted — [arXiv 2507.22478](https://arxiv.org/html/2507.22478)

### Inferences
- Estimate: 3,000 prompts × (~1,000 prompt tokens incl. DDL + ~500 output tokens) ≈ 4.5M tokens → ~20–30 min at 3–4k tok/s; ×8 samples for self-consistency/execution filtering ≈ 2–4 h (prompt prefix caching reduces this). On a 24GB consumer card at typical cloud rates this is a few USD (rental price not verified).
- Use greedy (temperature 0) for the main dataset, or sample n=4–8 at T≈0.7 and keep the response whose SQL executes and matches gold — record the filter rule.
- bf16 7B needs ~15GB weights; 24GB GPU suffices; avoid quantizing the teacher (would confound teacher quality).

### Gaps
- Benchmarks used short prompts (100 tokens); long schema prompts lower req/s — no source measured that case.
- Current (Oct 2026) cloud GPU hourly prices not verified.
